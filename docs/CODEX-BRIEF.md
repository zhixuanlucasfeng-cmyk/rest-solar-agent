# Brief: make the country admin console actually usable

Four country managers (Cameroon, Mali, Nigeria, Sudan) must each be able to
manage **their own** site: upload products, update stock, reply to messages,
manage orders. The code for all four exists. None of it is usable today.

Do not rewrite what works. Read "What is already correct" before touching
anything.

---

|---|---|---|---|

## What is already correct — do not redo

Country isolation in the console is genuinely implemented, not a stub:

- `app/admin/deps.py` — `scope_clause(user, model)` and `assert_visible(user, obj)`;
  superadmin (`country is None`) sees everything, others are pinned to their country.
- `app/admin/routes.py` — products (206-216), orders (399-430), conversations
  and tickets (70-74, 437-464) all apply it.
- Roles: `superadmin` / `country_admin` / `agent`. `require_admin` blocks the
  CS-only `agent` role from management pages; agents get the Inbox only.
- `app/countries.py` — CM/NG/SD/ML whitelist; anything else is rejected.
- `tests/test_admin_scope.py`, `tests/test_ws_handoff.py` cover this.

Handoff transport: `app/api/ws.py` (`/ws/admin/{user_id}` at :71,
`/ws/{conversation_id}` at :175, `_queue_snapshot` at :29) and
`app/api/ws_manager.py` (`ConnectionManager`, broadcasts per country).

## Task 1 — the service is not responding (blocks everything else)

Measured from one machine, 2026-09-24:

```
onrender.com                      HTTP 301, 1.5s    platform reachable
rest-solar-agent.onrender.com     HTTP 000, connect=0.000s
  /health   waited 1615s, TCP connection never established
  /api/chat HTTP 000 after 0.17s (fast fail)
```

DNS resolves (216.24.57.16, Cloudflare in front of Render). A cold start
connects first and *then* takes 30-60s for the first byte; connect time of
exactly 0.000s is not a cold start.

**Not independently confirmed** — the measuring machine is behind a UAE ISP that blocks
various traffic, and an external proxy check was inconclusive (it also failed
against a site known to be up). **First action: open the Render dashboard and
read the service status and deploy logs.** Suspended free service, failed
deploy, and crash-on-boot all look like this from outside.

Note this also means the AI chat widget on restarsolar.net is dead right now.

## Task 2 — configure `REDIS_URL`

Handoff queueing and cross-worker broadcast need Redis. It is not set on
Render. `app/api/ws.py` already degrades gracefully when Redis is unreachable
(commit `0afe343`), so this fails quietly rather than loudly — check it, do not
assume it works because nothing errored.

## Task 3 — the three data stores do not talk to each other

This is the real work, and the reason a manager who logs in today would find
the console useless even with the service up.

**Products.** The website renders from `camaroom-web/assets/data/products.js`,
a static file whose first line says "Generated by scripts/build_products.py —
do not edit by hand". The website makes **zero** requests to the agent
backend for products. A product uploaded in the console changes nothing that a
customer sees.

**Stock.** The website reads stock from the Cloudflare Worker's
`/api/inventory` (`camaroom-web/index.html:1098`). The console's
`Product.stock` (`app/db/models.py:58`) is a different field in a different
database that nothing on the website reads.

**Orders.** Two unrelated order systems:
- `Order` in Postgres — created from chat, has `conversation_id`, shown in the console
- `orders` in Cloudflare D1 — created by the website cart, invisible to the console

**A direction has to be chosen before coding.** Two options:

- **A — console becomes the source of truth.** Website fetches products and
  stock from the agent backend at runtime; `build_products.py` and
  `products.js` retire. Cart orders POST to the agent backend, or are mirrored
  into it. Biggest change, one system afterwards.
- **B — keep the split, add sync.** Console writes still regenerate
  `products.js` and push stock into the Worker's D1; cart orders are pulled
  into Postgres on a schedule. Less invasive, two systems forever, drift is
  permanent.

Do not pick this alone — confirm with the owner first.

## Task 4 — Nigeria and Sudan have no cart backend at all

`camaroom-web/assets/js/countries.js`: `cart_backend` is a URL for CM and ML,
`null` for NG, SD and OTHER. For those two countries "update stock" and
"manage orders" are not broken features, they are absent infrastructure.

Either deploy a Worker + D1 per country (the code is country-agnostic; see
`wrangler.mali.toml` as the template) or tell those two managers plainly that
they have messaging only for now.

## Task 5 — the Cloudflare admin pages share one password

`camaroom-web/backend/src/auth.js` — `checkPassword()` compares against a
single `ADMIN_PASSWORD` env var. The Worker's `/admin/inventory`,
`/admin/shipments` and `/admin/quote/{id}` pages have no per-person and no
per-country accounts. Four managers would share one credential and could each
edit the others' data.

If Task 3 lands on option A this disappears, since the console already has
real accounts. If option B, these pages need per-country auth.

## Definition of done

A manager for each of the four countries can log in and:

1. see only their own country's products, orders and conversations
2. upload a product and **see it on restarsolar.net for their country**
3. change stock and **see the website's stock badge change**
4. open the Inbox, receive a handoff request, and reply to a live customer
5. see the orders their customers actually placed — cart orders included

Verify 2, 3 and 5 end to end in a browser against the live site, not by
reading code. 1 and 4 have tests; run them.
